# 01 · 原理

> 本文解释三件事：车机上到底有哪两个"工程模式"、USB 切换最终写到了哪里、
> 以及为什么普通应用直接抄代码没用。

---

## 1. 两个"工程模式"

车友口中的"工程模式"可能指两个完全不同的东西：

| | MTK EngineerMode | 长安 TSP Factory |
|---|---|---|
| 包名 | `com.mediatek.engineermode` | `com.chinatsp.tfactoryapp` |
| 来源 | 联发科平台自带 | 长安自研 |
| 入口 | 拨号盘暗码 / 特定 Activity | 设置里的隐藏入口 / 广播 |
| 菜单 | Hardware Testing、USB、ATCI 等 | LOG 日志、USB 切换、车型配置、TBox、写入 VIN、OTA 工程模式等 16 项 |
| 与 ADB 的关系 | 写 `sys.usb.config`，普通应用无权限 | 写 MCU 属性，走 CarService |

本车实际用的是 **长安 TSP Factory**。MTK 的 EngineerMode 即使存在，其 USB 菜单在
量产 user 版里也会被移除，所以不要照着 MTK 的代码找入口。

---

## 2. TSP Factory 的两道门

### 2.1 第一道：6 位 PIN

- 打开 TSP Factory 的 `MainActivity`（exported）后，先进入 6 位数字键盘页；
- 输入值与资源里的一个 MD5 校验值做比对；
- 这只是一道**界面门**，不参与后续的属性写入。

PIN 的具体值不在本仓库公开。

### 2.2 第二道：切换前的二级认证

- 点"切换为 ADB 模式 / U 盘模式"时，会要求"安全开启工程模式"的车端认证；
- 认证绑定手机号，属于云端/账号体系；
- **这道认证只挡 UI 操作**：它不会阻止其他进程直接写底层属性。

这解释了一个常见困惑：

> 为什么我自动化点击走不通，但直接写属性却可以？

因为自动化走的是 UI 路径，必须过第二道门；直接写属性绕开了 UI，只面对 CarService
的入口校验。

---

## 3. USB 切换的真实落点

TSP Factory 的"USB 切换"最终执行的是：

```
UsbFragment
  → CarMcuManagerUtil.setMcuModeSelect(mode)
    → CarMcuManager.ID_MCU_USB_MODE_SELECT = 557921325  (0x2141342D, vendor 段)
      → CarService → VHAL → MCU
```

`mode` 的取值：

| 值 | 含义 |
|---|---|
| 1 | ADB 模式 |
| 2 | U 盘模式 |

也就是说，切换的本质不是改 Android 的 USB 配置字符串，而是让 **MCU 物理切换 USB 口的
host/device 角色**。这带来两个直接后果：

1. 切到 U 盘模式后，`adb devices` 会消失，因为 USB 口不再以 device 角色暴露 ADB；
2. 常见的 `sys.usb.config` 或 `Settings.Global.adb_enabled` 写法**不会**改变这个状态，
   因为这条链路上没有监听者。

### 3.1 与常见 Android 机制的区别

| 机制 | 写入目标 | 谁监听 | 在本车是否有效 |
|---|---|---|---|
| 开发者选项 USB 调试 | `Settings.Global.adb_enabled` | `system_server` 的 UsbDeviceManager | 对"ADB 功能开关"有效，但对 MCU 的 host/device 角色无效 |
| MTK EngineerMode | `sys.usb.config` | init / USB HAL | 需要 radio/platform 域权限，普通应用不可写 |
| TSP Factory | MCU 属性 `557921325` | CarService → VHAL → MCU | 有效，是本文讨论的路径 |

## 4. CarService 的入口校验

普通应用调用 `getCarManager("mcu")` 或 `getCarManager("property")` 时，会先过
CarService 的入口检查。反编译与实车结果如下：

### 4.1 检查发生在哪里

```
ICarImpl.getCarService
  → CarServiceUtils.isHaveSecurityPermission
    → 取 Binder 调用方的 PID
    → 查 RunningAppProcessInfo.processName
    → 判断进程名是否在硬编码列表里
```

关键点：

- 查的是**进程名**，不是包名、UID 或签名；
- 列表硬编码在 `CarServiceConstant` 中（约 170 项）；
- 不在列表里会抛 `SecurityException: <pkg> is not in white list!`。

### 4.2 为什么"只看进程名"是个弱点

Android 允许应用通过 `AndroidManifest.xml` 的 `android:process` 指定进程名。
如果校验只看进程名，那么进程名的可信度就成了整个校验的根基。

本仓库不提供具体的白名单进程名，也不提供完整绕过代码。这里只记录结论：

> 在 2026-08 的固件上，进程名校验可以通过声明同名进程满足；进入后，
> 属性读写层的权限检查未实际拦截（`assertPermission` 丢弃了检查结果）。

### 4.3 影响面

一旦通过入口校验，应用就能拿到 `mcu` / `property` 等 CarManager，进而读写
vendor 段属性。`557921325` 只是其中一个；其他属性的风险取决于其语义
（例如电源、驱动、灯光）。**不要因为"能写"就去写**。

## 5. 为什么不能照抄 MTK 的代码

MTK EngineerMode 里的三种写法，在普通应用里都不可行：

| 写法 | 失败原因 |
|---|---|
| `SystemProperties.set("sys.usb.config", ...)` | SELinux 拦截，普通应用没有 `set_prop` 权限 |
| `ShellExe` → emsvr LocalSocket | 本车没有 `/dev/socket/EngineerModeServer`，且 EM 以 radio uid 运行 |
| HIDL `IEmd.setUsbPort()` | untrusted_app 无 HIDL 访问权 |

根本原因：

> **权限跟着进程域（签名 + 安装位置 + SELinux 域）走，不跟代码走。**
> 把系统应用的代码复制到普通应用里，代码能编译，但权限不会跟过来。

---

## 6. 小结

- 本车的 USB 切换是 MCU 属性，不是 Android USB 配置；
- 界面层的 PIN 与二级认证不保护底层属性；
- CarService 的入口校验依赖进程名，这是路径 B 成立的前提；
- 普通应用复制系统应用代码无效，因为权限在进程域，不在代码。
