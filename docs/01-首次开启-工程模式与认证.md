# 01 · 首次开启：工程模式与认证绕过

> 目标：在**不改车机、不拆机、不 root** 的前提下，让车机自己把 USB 切换到 ADB 模式。
>
> 关键结论：工程模式的二级认证只挡 UI，**不校验服务端证书**。只要在笔记本上冒充
> 认证服务端并返回成功，车机就会放行"切换为 ADB 模式"。

---

## 1. 前置条件

| 项目 | 要求 |
|---|---|
| 车机 | 长安启源 C589 PHEV / 启源 OS（Android 9），其他车型需自行验证 |
| 笔记本 | Windows 10/11，Python 3.8+（标准库即可） |
| 网络 | 笔记本能开 Wi-Fi 热点，车机可连接 |
| 权限 | 笔记本上有管理员权限（写 hosts、绑 443 端口） |
| 其他 | 关闭 Clash / VPN 等会接管 DNS 或 443 的软件 |

---

## 2. 认证在工程模式里的位置

```
TSP Factory MainActivity
  → 6 位 PIN 门
    → 二级认证（"安全开启工程模式"，绑定手机号）
      → 菜单「USB 切换」
        → 切换为 ADB 模式 / U 盘模式
          → CarMcuManager.setMcuModeSelect(1|2)
            → ID_MCU_USB_MODE_SELECT = 557921325
              → CarService → VHAL → MCU
```

二级认证的作用只有一个：**决定 UI 是否允许你点那个按钮**。
它不参与后续的属性写入，也不在 MCU 侧做额外校验。

---

## 3. 认证协议

### 3.1 接口

```
POST https://spm.auto-pai.com/tlc/auth/v1/sms
POST https://spm.auto-pai.com/tlc/auth/v1/login
POST https://spm.auto-pai.com/tlc/auth/v1/authQuery
```

### 3.2 请求体结构

抓包得到的 `login` 请求（值已脱敏）：

```json
{
  "appid": "<APPID>",
  "timestamp": "<毫秒时间戳>",
  "nonce": "<32 位随机串>",
  "signVersion": "V2.0",
  "sdkVersion": "1023",
  "data": "{\"phone\":\"<PHONE>\",\"captcha\":\"<CODE>\",\"tuid\":\"<TUID>\",\"vin\":\"<VIN>\"}",
  "sign": "<签名>"
}
```

要点：

- `data` 是一个 **JSON 字符串**（不是对象），里面才是 phone/captcha/tuid/vin；
- 服务端是否校验 `sign`，取决于实现；在本项目的假服务器里不校验；
- 客户端没有对响应做签名校验，只看 `code`。

### 3.3 期望响应

```json
{"code": "0000", "message": "success", "data": "<phone>"}
```

`code` 为 `0000` 即视为成功。`data` 原样回显手机号即可。

## 4. 为什么能被绕过

反编译该 App 的网络层，有两个关键实现：

### 4.1 信任所有证书

```java
// 等价逻辑（示意）
X509TrustManager tm = new X509TrustManager() {
    public void checkClientTrusted(X509Certificate[] chain, String authType) {}
    public void checkServerTrusted(X509Certificate[] chain, String authType) {}
    public X509Certificate[] getAcceptedIssuers() { return new X509Certificate[0]; }
};
HostnameVerifier hv = (hostname, session) -> true;
```

这意味着：**任何自签证书、任何域名都接受**。我们不需要车机的证书，
也不需要 CA，只要在 `spm.auto-pai.com:443` 上放一个自签证书即可。

### 4.2 只看 `code`

客户端解析响应时只判断 `code == "0000"`，不校验 `message`、`data` 的内容，
也不校验响应签名。所以假服务器返回固定 JSON 就能通过。

### 4.3 结论

> 这套认证的信任边界完全依赖"域名解析到真实服务器"。
> 一旦域名被指向本地，证书和响应都可以伪造。

## 5. 方案：热点 + hosts/DNS + 自签 HTTPS

### 5.1 拓扑

```
┌──────────────┐        Wi-Fi 热点         ┌─────────────────────┐
│   车机        │ ───────────────────────> │  笔记本              │
│              │                          │  192.168.137.1       │
│ spm.auto-    │   HTTPS :443             │  ├ hosts/DNS 劫持     │
│ pai.com      │ <─────────────────────── │  ├ 自签证书           │
│              │                          │  └ 假认证服务器        │
└──────────────┘                          └─────────────────────┘
```

### 5.2 让域名指向笔记本

两种方式，任选其一：

**方式 A：hosts（推荐）**

在笔记本的 `C:\Windows\System32\drivers\etc\hosts` 增加一行：

```
192.168.137.1  spm.auto-pai.com
```

注意：hosts 只影响**发起请求的那台机器**。车机的 DNS 请求发往笔记本，
所以更准确的做法是让笔记本作为车机的 DNS 服务器，或者在热点网关上做重定向。
本项目脚本同时提供 hosts 与迷你 DNS 两种方式：

- 如果车机把热点电脑当作 DNS（Windows 移动热点默认会下发自身为网关/DNS），
  hosts 通常就能生效；
- 如果不生效，用脚本的 `--dns` 模式，在 53 端口直接应答该域名。

**方式 B：迷你 DNS**

脚本在 UDP 53 上监听，把 `spm.auto-pai.com` 应答为 `192.168.137.1`，
其余查询转发上游。需要关闭会占用 53 端口的软件。

### 5.3 自签证书

```bash
openssl req -x509 -newkey rsa:2048 -nodes \
  -keyout server.key -out server.crt -days 3650 \
  -subj "/CN=spm.auto-pai.com"
```

因为车机不校验证书，CN 是否匹配都不影响；写成目标域名只是为了清晰。

### 5.4 假服务器

见 [examples/fake_tlc_server.py](../examples/fake_tlc_server.py)。核心逻辑：

```python
if path.endswith("/tlc/auth/v1/sms"):
    resp = ok_resp(data=phone)
elif path.endswith("/tlc/auth/v1/login"):
    resp = ok_resp(data=phone)
elif path.endswith("/tlc/auth/v1/authQuery"):
    resp = ok_resp(data="")
else:
    resp = ok_resp(code="E99999")

def ok_resp(code="0000", data=""):
    return json.dumps({"code": code, "message": "success", "data": data}).encode()
```

再加上：

- 443 端口 + `ssl.SSLContext.wrap_socket`；
- 管理员权限（Windows 绑定 443）；
- 退出时清理 hosts。

## 6. 操作步骤

```bash
# 1) 生成证书（只需一次）
cd examples
bash gen_cert.sh

# 2) 启动假服务器（会自动请求管理员权限）
python fake_tlc_server.py

# 3) 车机连笔记本热点
# 4) 车机进入工程模式 → 任意手机号 + 任意验证码 → 登录
# 5) 看到"登录成功"后，点「切换为 ADB 模式」
# 6) 在笔记本上确认
adb devices
```

脚本日志里能看到车机请求打进来，说明劫持生效：

```
>>> POST /tlc/auth/v1/login 来自 192.168.137.103（证书校验通过）
<<< 返回: {"code": "0000", "message": "success", "data": "<PHONE>"}
```

## 7. 排错

| 现象 | 原因 | 处理 |
|---|---|---|
| 车机登录转圈/失败 | 域名仍解析到真实服务器 | 断开重连 Wi-Fi、重启车机；或改用 `--dns` |
| 脚本绑 443 失败 | 无管理员权限 | 用管理员终端运行；或 `--port 8443` 自测 |
| `--dns` 绑 53 失败 | Clash/VPN 占用 53 | 退出代理软件 |
| 登录成功但切换仍失败 | 没点"切换为 ADB 模式"，或车机有额外校验 | 看 [04-验证记录.md](04-验证记录.md) |
| `adb devices` 仍为空 | USB 模式未切换 / 线材或驱动问题 | 先看车机 USB 通知，再查驱动 |

---

## 8. 安全边界

- 这套方法**只影响认证 UI**，不会让车机执行任意代码；
- 假服务器不向车机下发任何内容，只回固定 JSON；
- 但它确实绕过了厂商的认证设计，可能违反服务条款；
- **仅在你自己的车上使用**，不要做成"帮人开 ADB"的服务；
- 不要在公共网络、公司网络或他人热点上运行。
